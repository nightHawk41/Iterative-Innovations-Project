Sprint 3 Goal:
Revamp the frontend to match the vending1.html prototype: a persistent 6x4 machine
grid, sidebar with Dashboard/Admin tab switching, a slot purchase flow, admin panel
enhancements, and the new backend endpoints that support them.

Already Completed (no action needed):

  - Dashboard stats header: Total Slots, Healthy, Low/Expiring, Critical (DashboardPage.js)
  - Transaction CSV file picker and POST /api/transactions/process call (TransactionUpload.js)

Implementation Order Note:
Backend tasks should be completed before the frontend tasks that depend on them.
Frontend tasks marked with [DEPENDS ON ...] must wait for the referenced backend task.
Resolve the architecture decision in Task A-1 before beginning any Phase 1 frontend work.

------------------------------------------------------------
ARCHITECTURE DECISION
------------------------------------------------------------

[TASK A-1] Migrate the app shell to the prototype's persistent two-column layout.
  Decision: adopt the prototype layout -- sidebar with Dashboard/Admin tab switching,
  machine grid always visible on the right, no page-level navigation.

  Required changes to the existing codebase:
    - App.js: remove React Router (<Routes>, <Route>, <Navigate>). Replace with a
      two-column shell: left sidebar (fixed width) + right machine panel (flex: 1).
      A single tab state value ("dashboard" | "admin") controls which sidebar content
      is visible; the machine grid renders unconditionally in the right panel.
    - Sidebar.js: remove NavLink-based navigation. Replace with two tab buttons
      (Dashboard / Admin) that toggle the sidebar content via the tab state.
    - DashboardPage.js: dissolve this page component. Move its stats header and
      AlertsBanner into the Dashboard tab content area of the sidebar.
    - AdminPage.js: dissolve this page component. Move its admin controls
      (restock, CSV uploads, sales report) into the Admin tab content area.
      The InventoryGrid inside AdminPage is removed; the grid is now the shared
      right panel and does not belong to either tab.
    - Remove react-router-dom from the project if no other code uses it after
      the migration, and remove the corresponding import in index.js.

FRONTEND: Phase 1 -- Vending Machine Grid
------------------------------------------
[TASK F-1] Replace the Accordion layout in InventoryGrid.js with a static 6x4 CSS grid.
	The grid must span rows A-F and columns 1-4, producing exactly 24 slot cells.
	Ensure column indexing is 1-based (columns 1-4) so slots are labeled A1, A2... instead of A0.
	Remove the existing Accordion, groupByRow logic, Expand All / Collapse All buttons,
	and the react-bootstrap Accordion import.
	Render all 24 SlotCard components directly in the grid without any row grouping.

[TASK F-2] Update SlotCard to match the vending machine slot display.
	Each slot must show: position label (e.g., "A1"), product name, price, stock count,
	and expiration countdown ("Exp: Nd" or "⚠ Expired" if days_until_expiry <= 0).
	Note: Apply the "strict rule" where 0 days remaining evaluates as Expired.
	Remove the existing StatusIndicator badge and left-border color styling.
	Apply background color directly to the slot cell based on status (see Task F-3).

[TASK F-3] Implement status color and disabled-state logic in SlotCard.
	Color rules (applied as the slot's background color):
	- Gray   (#aaa, disabled):        stock === 0 OR days_until_expiry <= 0 (strict expiration rule)
	- Red    (#e53935 / white text):  stock <= 2 OR days_until_expiry <= 2
	- Yellow (#f5c518 / dark text):   stock <= 5 OR days_until_expiry <= 5
	- Green  (#5db85d / white text):  stock > 5 AND days_until_expiry > 5
	Confirm whether the backend's status_color field already matches these exact thresholds.
	If thresholds differ, decide whether to use the backend value or recalculate on the frontend.
	Disabled slots must not respond to clicks and must render at reduced opacity.

[TASK F-4] Make non-disabled slots interactive: clicking opens a purchase confirmation modal.
	The modal must display the item name, slot position (e.g., "A1"), and price.
	Modal prompt format: "Purchase [item name] (Slot [position]) for $[price]?"
	Use a React modal overlay (not window.confirm()) with Confirm and Cancel buttons.
	Purchase interaction is only active when the Dashboard tab is selected.
	When the Admin tab is active, all slots must be non-clickable (pointer-events: none
	or equivalent) even if they are not otherwise disabled.
	[DEPENDS ON B-1]

[TASK F-5] Implement purchase confirmation logic wired to the backend.
	On confirm: send POST /api/purchase with { "slot_id": "<id>", "quantity": 1 }.
	On success: decrement the displayed stock for that slot, re-render the grid, and show a success toast.
	On failure (e.g., out of stock): close the modal and show an error toast.
	On cancel: close the modal without any changes.
	This flow must never be reachable from the Admin tab (enforced by Task F-4).
	[DEPENDS ON B-1]

BACKEND: Phase 4 -- New Endpoints
---------------------------------
[TASK B-1] Implement POST /api/purchase (api/inventory_routes.py).
	Request body (JSON): { "slot_id": "A1", "quantity": 1 }.
	Behavior: look up the slot, confirm stock > 0 and days_until_expiry > 0, decrement by quantity, persist, and return updated slot. Note: This endpoint should also generate and append a transaction record to the database for sales reporting.
	On success (200): return updated slot dict + { "message": "Purchase successful" }.
	On out-of-stock, expired, or concurrent write conflict (409): return a ConcurrencyError-style response
	consistent with the existing D-2 pattern used in restock and transaction routes.
	On unknown slot_id (400): return a descriptive error message.
	This endpoint is a hard dependency for frontend Tasks F-4 and F-5.

[TASK B-2] Implement POST /api/inventory/upload (api/inventory_routes.py).
	Accepts a CSV file upload (multipart/form-data, field name = "file").
	Expected CSV columns must match the schema of the existing inventory_config.csv.
	Behavior: parse the uploaded CSV, clear all existing ItemSlot rows, seed with new rows.
	On success (200): return { "message": "Inventory uploaded", "slot_count": <int> }.
	On bad file format or parse error (400): return a descriptive error without touching the database.

[TASK B-3] Implement GET /api/sales-report (api/transaction_routes.py).
	Aggregate data from the database transactions to produce a sales report.
	Report columns: rank, slot_id, item_name, total_units_sold, total_revenue, avg_price.
	Return the report as a downloadable CSV file or structured JSON payload to power the new Sales Report window.
	If no transactions have been processed yet, return 404 with a descriptive message.

[TASK B-4] Implement POST /api/reset (api/inventory_routes.py).  [CONDITIONAL -- see Task F-6]
  Re-run the seed script to restore the database to its original default state.
  On success (200): return { "message": "Machine reset to default state" }.
  Only implement this task if the Reload button in Task F-6 is implemented as Option B
  (full machine reset). If Option A (re-fetch only) is chosen, this task is not needed.
