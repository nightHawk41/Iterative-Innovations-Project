B-02: Add slot_id label format validation
vending.html uses labels like A0, A1, A2, A3 (0-indexed columns). The current inventory_config.csv uses A1–A4 (1-indexed). Decide on one convention and apply it consistently to the seed file, the config CSV, and the frontend slot label generator (slotLabel(i)). The decision is to use A1–A4 (1-indexed). 

B-01: Add GET /api/inventory endpoint response alignment
The frontend reads slot_id, item_name, price, quantity, days_until_expiry, and status_color. Verify to_dict() on ItemSlot returns all of these with matching key names. Currently, days_until_expiry is returned, but vending.html uses days_until_expiration — standardize one name across the backend and frontend. The decision is to use days_until_expiry.

B-03: Add GET /api/inventory/summary endpoint
The Dashboard tab shows the counts for Total Slots, Healthy, Low/Expiring, and Critical/Out. Currently, these are computed in JavaScript. Add a backend endpoint that returns these four counts so the frontend can fetch live data instead of computing from the full inventory list.

Phase 2 — Purchase Flow (Single-Item Grid Purchase)
----------------------------------------------------------------
B-05: Add CBORD transaction log builder utility
Extract the random patron data generation from the purchase flow into a reusable utility function. This mirrors logTransaction() in vending.html and should generate:
A random Primary Key (auto-incrementing patron ID)
A random Patron Name from a predefined list
A random SV&C Plan (35 RETRIEVER, 45 DEPT., 40 COMMUTER)
A random Period (Breakfast, Lunch, Afternoon, Dinner, Evening)
Current timestamp as Transaction Date
Location hardcoded to 1499 Lib_Sup
Tran Amt set to the slot's price
Stat hardcoded to C

B-04: Add POST /api/purchase endpoint
vending.html allows users to click a slot and confirm a purchase. Currently there is no endpoint for a single ad-hoc purchase outside of CSV processing. This endpoint should:
Accept { "slot_id": "A1" } in the request body
Look up the slot by slot_id
Verify stock > 0 and item is not expired
Decrement stock by 1
Generate and persist a CBORD-style Transaction record with randomized patron data (matching the logTransaction() behavior in vending.html)
Return the updated slot dict
Return 409 if out of stock (D-2 safeguard)
Return 400 if slot is expired or does not exist

B-06: Add GET /api/transactions endpoint
The Generate Sales Report button needs access to all logged transactions — both from grid purchases and from uploaded CSVs. Add an endpoint that returns all Transaction rows, ordered by timestamp descending, serialized to dict.

Phase 4 — Sales Report Generation
---------------------------------------------
B-10: Add GET /api/reports/sales endpoint
The Generate Sales Report button currently calls openSalesReport() using in-memory data. Move report aggregation to the backend. This endpoint should:
Read all Transaction rows from the database that have a non-null resolved_slot_id
Join against ItemSlot to get item_name
Aggregate by item: units sold, total revenue, average price
Return sorted by total revenue descending
Include summary fields: total_revenue, total_units, unique_items, date_range, generated_at, top_item

B-11: Add report availability guard
The Generate Sales Report button should only be enabled when at least one transaction exists. Add a field to the GET /api/reports/sales response (or a separate GET /api/transactions/count endpoint) so the frontend can check whether any transactions are logged before enabling the button.

vending.html has an Upload New Inventory CSV panel that updates item names, prices, and optionally stock and expiration. This maps to the existing POST /api/admin/sync-inventory-config endpoint, but that endpoint reads from a file path on disk rather than accepting a file upload. Modify it (or add a new endpoint) to accept a multipart file upload with the inventory_config.csv column structure (ROW, Product, Vending Price, optional stock, optional expiration_date).
B-13: Handle optional stock and expiration_date columns in seed
